# MT7621 SDK 交叉编译实录

本文记录一次为 MT7621（`mipsel_24kc` / musl）构建 MiniMihomo 的完整过程。目标不是覆盖 OpenWrt 的所有构建方式，而是把这次实际遇到的环境问题、判断依据和可复用的处理方法留下来，便于以后换 SDK、换硬件或升级源码时排查。

> 本文中的 SDK、源码和构建产物都保存在本地；没有把 SDK 的临时修改提交到插件源码仓库。

## 1. 本次结果

目标 SDK：

```text
OpenWrt SDK 23.05.4
target: ramips/mt7621
arch: mipsel_24kc
libc: musl
```

成功得到的包：

```text
bin/packages/mipsel_24kc/minimihomo/mihomo_git-r1_mipsel_24kc.ipk
```

## 2. 目录与源码关系

本次工作目录如下：

```text
/home/data/workspace/openwrt/TestOpenwrt/
├── minimihomo-feed/
│   ├── luci-app-minimihomo/       # LuCI 插件源码
│   └── mihomo-openwrt/            # OpenWrt 核心包 Makefile

└── openwrt-sdk-23.05.4-ramips-mt7621_gcc-12.3.0_musl.Linux-x86_64/

```

这里的关键原则是：核心代码来自本地 `mihomo-source`，而非构建时重新从互联网下载。`mihomo-openwrt/Makefile` 应引用本地源码目录，LuCI 插件则由本地 `luci-app-minimihomo` 源码打包。

构建链路可简化为：

```text
本地 mihomo-source
        │
        ▼

        │  GOOS=linux GOARCH=mipsle GOMIPS=softfloat
        ▼
MT7621 mihomo ELF 二进制
        │
        ▼
OpenWrt IPK 封装
        │
        └── mihomo_git-r1_mipsel_24kc.ipk

本地 luci-app-minimihomo 源码 ──► luci-app-minimihomo_2.0.0-r17_all.ipk
```

## 3. SDK 初始检查

进入 SDK 后，先检查目标、宿主工具和包源是否正确。以下变量仅为便于阅读，路径可按自己的目录调整：

```sh
PROJECT=/home/data/workspace/openwrt/TestOpenwrt
SDK="$PROJECT/openwrt-sdk-23.05.4-ramips-mt7621_gcc-12.3.0_musl.Linux-x86_64"
cd "$SDK"
```

建议先确认：

```sh
grep -E 'CONFIG_TARGET_(ramips|ramips_mt7621)|CONFIG_TARGET_ARCH_PACKAGES' .config
find feeds -maxdepth 2 -type l -o -type d | grep minimihomo
```

预期重点是 `ramips_mt7621` 和 `mipsel_24kc`。如果架构不对，后续即使成功编译，路由器也无法执行核心程序。

## 4. 第一类问题：SDK 前置检查找不到 GNU install

最初执行 `make` 时，SDK 报：

```text
Build dependency: Please install GNU 'install'
Prerequisite check failed.
```

原因不是没有安装 `coreutils`，而是宿主系统默认的 `install` 实际来自 uutils；SDK 的旧版检查脚本要求 GNU coreutils 的实现。

系统中已经存在 GNU 版本 `/usr/bin/gnuinstall`。最小影响的处理方式不是替换系统命令，而是在 SDK 内创建一个仅供此次构建使用的工具优先目录：

```sh
cd "$SDK"
mkdir -p .host-tools
ln -sf /usr/bin/gnuinstall .host-tools/install
PATH="$PWD/.host-tools:$PATH" make defconfig
```

以后执行 SDK 的 `make` 时都保留此前缀：

```sh
PATH="$PWD/.host-tools:$PATH" make <目标>
```

这相当于只对该 SDK 告诉构建系统：优先使用 GNU `install`；不会改变系统全局的命令行为。

## 5. 第二类问题：SDK 配置意外选择了全部硬件与内核模块

### 5.1 现象

原始 SDK 的配置生成规则带有不合适的静态默认值。即使只是执行单个包的编译，仍会选择：

- 所有 MT7621 设备 profile；
- `ALL`、`ALL_NONSHARED`、`ALL_KMODS`；
- 大量内核模块与固件包。

结果是构建过程开始处理完整内核、海量模块，甚至下载数百 MB 的固件归档。之后还可能因不需要的模块依赖（例如 `bonding` 所需的 `tls.ko`）中断。这不是 MiniMihomo 代码本身的错误，而是 SDK 配置范围过大。

### 5.2 处理思路

只保留一个 MT7621 设备 profile，用它建立有效的目标配置；关闭“全部包/全部模块”类选项，只保留核心运行依赖 `kmod-tun`。

在修改前先备份，SDK 的这些改动是本地构建修补，不应提交进插件仓库：

```sh
cd "$SDK"
cp Config-build.in Config-build.in.before-minimal
cp .config .config.before-minimal
```

需要关注的配置项：

```text
CONFIG_TARGET_MULTI_PROFILE
CONFIG_TARGET_ALL_PROFILES
CONFIG_TARGET_PER_DEVICE_ROOTFS
CONFIG_ALL
CONFIG_ALL_NONSHARED
CONFIG_ALL_KMODS
CONFIG_PACKAGE_kmod-*
```

可先在 `.config` 中清掉已经被选中的模块，再明确保留 TUN：

```sh
perl -pi -e 's/^(CONFIG_PACKAGE_kmod-[^=]+)=m$/# $1 is not set/' .config
sed -i 's/^# CONFIG_PACKAGE_kmod-tun is not set$/CONFIG_PACKAGE_kmod-tun=m/' .config
sed -i -E 's/^CONFIG_(ALL|ALL_NONSHARED)=y$/# CONFIG_\1 is not set/' .config
```

如果运行 `make defconfig` 后这些选项又被自动打开，说明根源在 `Config-build.in` 的 `default y`，而不是 `.config`。需要将以下类别的默认值从 `y` 改为 `n`：

```text
TARGET_MULTI_PROFILE
TARGET_ALL_PROFILES
TARGET_PER_DEVICE_ROOTFS
ALL
ALL_NONSHARED
ALL_KMODS
不需要的 TARGET_DEVICE_ramips_mt7621_DEVICE_*
不需要的 PACKAGE_kmod-*
```

本次只保留了一个 MT7621 设备（`xiaomi_mi-router-4a-gigabit`）以满足 Kconfig 的设备选择要求。该选择用于生成最小 SDK 配置，并不把 Mihomo 二进制限定为这一个路由器型号；二进制仍以 `mipsel_24kc` 为目标。

修改后重新整理配置：

```sh
PATH="$PWD/.host-tools:$PATH" make defconfig
```

然后再检查：

```sh
grep -E 'CONFIG_(ALL|ALL_NONSHARED|ALL_KMODS|TARGET_MULTI_PROFILE|TARGET_ALL_PROFILES)' .config
grep '^CONFIG_PACKAGE_kmod-' .config
```

预期是不再出现 `=y` 的全量选择；`kmod-tun` 按需保留。

## 6. 第三类问题：OpenWrt 23.05 SDK 的 Go host 编译与新 GCC C23 不兼容

Mihomo 需要 Go。宿主机没有可直接使用的 Go，因此先让 SDK 构建自己的 Go host 工具：

```sh
PATH="$PWD/.host-tools:$PATH" \
make package/feeds/packages/golang/host/compile V=sc
```

第一次失败，错误类似：

```text
typedef int bool;
bool is a keyword with -std=c23 onwards
```

原因是 SDK 内的旧 Go 引导源码与当前宿主 GCC 默认启用的 C23 语义不兼容。

不要把 `HOSTCC_NOCACHE='gcc -std=gnu17'` 直接传给 Go：Go 的构建流程会把 `CC` 当作单个可执行文件路径，带空格的字符串会导致“找不到 `gcc -std=gnu17`”的后续错误。

正确方式是创建一个无空格名称的编译器包装器：

```sh
cd "$SDK"
mkdir -p .host-tools
```

在 `.host-tools/gcc` 中写入：

```sh
#!/bin/sh
exec /usr/bin/gcc -std=gnu17 "$@"
```

并授权：

```sh
chmod 755 .host-tools/gcc
```

随后构建 SDK Go host：

```sh
PATH="$PWD/.host-tools:$PATH" \
make HOSTCC_NOCACHE="$PWD/.host-tools/gcc" \
  package/feeds/packages/golang/host/compile V=sc
```

本次该步骤最终成功。它耗时较长（约十分钟），但只要 SDK 和宿主编译器环境不变，后续通常不需要重复构建。

## 7. 编译 MT7621 Mihomo 核心

### 7.1 为什么没有直接使用 package/mihomo/compile

传统目标 `make package/mihomo/compile` 在 feed 包环境中通常不存在；正确的 feed 路径应类似：

```sh
make package/feeds/minimihomo/mihomo-openwrt/compile V=s
```

但本次 SDK 即使经过精简，仍被旧配置规则牵连到不相关的内核依赖。为保证“使用本地 Meta 源码”和“生成正确 MT7621 二进制”两个核心目标，改为使用已经由 SDK 构建好的 Go host 编译器直接编译源码，然后再按 OpenWrt 规范封装 IPK。

这不是使用宿主机随意交叉编译：真正执行 Go 编译的是 SDK 产生的 Go 工具，且目标参数明确为 Linux/MIPS little-endian/soft-float。

### 7.2 实际命令

```sh
cd "$SDK"
SDK_GO="$PWD/staging_dir/hostpkg/bin/go"

cd ../mihomo-source
GOOS=linux GOARCH=mipsle GOMIPS=softfloat CGO_ENABLED=0 \
  "$SDK_GO" build -trimpath -tags 'with_gvisor' -ldflags='-s -w' \
  -o /tmp/mihomo-mt7621 .
```

参数说明：

| 参数 | 作用 |
| --- | --- |
| `GOOS=linux` | 路由器运行 Linux。 |
| `GOARCH=mipsle` | 生成 MIPS 小端二进制，匹配 `mipsel_24kc`。 |
| `GOMIPS=softfloat` | 使用软浮点，匹配常见 OpenWrt MIPS/musl 目标。 |
| `CGO_ENABLED=0` | 生成不依赖 CGo 的静态 Go 程序，避免交叉 C 库链接问题。 |
| `-tags with_gvisor` | 保留本次核心所需的 gVisor 能力。 |
| `-trimpath` | 不把本机绝对源码路径写进二进制调试信息。 |
| `-ldflags='-s -w'` | 移除符号与 DWARF 调试信息以减小体积。 |

常见路径错误：在 SDK 内应使用 `../mihomo-source`，而不是 `../../mihomo-source`。前者从 SDK 目录返回到项目根目录后即可进入源码目录。

### 7.3 验证二进制

```sh
file /tmp/mihomo-mt7621
readelf -h /tmp/mihomo-mt7621 | rg 'Class:|Data:|Machine:'
```

本次结果的关键字段：

```text
ELF 32-bit LSB executable
MIPS
statically linked
stripped
Class: ELF32
Data: 2's complement, little endian
Machine: MIPS R3000
```

`readelf` 的 `MIPS R3000` 是 ELF 机器类别标签，不代表实际只适配 R3000。真正决定本次 Go 目标的是 `GOARCH=mipsle`、`GOMIPS=softfloat`，并与 SDK 包架构 `mipsel_24kc` 一致。

## 8. 手工封装为 OpenWrt IPK

### 8.1 准备安装根目录和控制信息

```sh
STAGE=/tmp/mihomo-ipk
OUT_DIR="$SDK/bin/packages/mipsel_24kc/minimihomo"

rm -rf "$STAGE"
mkdir -p "$STAGE/CONTROL" "$STAGE/usr/bin" "$OUT_DIR"
install -m 0755 /tmp/mihomo-mt7621 "$STAGE/usr/bin/mihomo"
```

`$STAGE/CONTROL/control` 内容为：

```text
Package: mihomo
Version: git-r1
Depends: ca-bundle, ip-full, kmod-tun
Architecture: mipsel_24kc
Maintainer: MiniMihomo
Description: Mihomo Meta proxy core
```

依赖说明：

- `ca-bundle`：HTTPS 订阅及 HTTPS 节点通常需要根证书。
- `ip-full`：透明代理/路由规则相关操作依赖完整 ip 工具。
- `kmod-tun`：启用 TUN 模式时需要；即便当前配置暂不开 TUN，保留该依赖可避免用户后续启用时缺少内核模块。

### 8.2 打包

SDK 自带的 `fakeroot` 由于其预加载库路径问题无法直接使用。曾尝试通过 `LD_LIBRARY_PATH=staging_dir/host/lib` 解决，但这会让系统 `/usr/bin/env` 误加载 SDK 的旧 glibc，出现缺少 GLIBC 符号的错误，因此不要采用该方案。

本次可用的组合是：系统 `fakeroot` + SDK 的 `scripts/ipkg-build`：

```sh
cd "$SDK"
fakeroot bash scripts/ipkg-build -m '' /tmp/mihomo-ipk "$OUT_DIR"
```

注意输出目录必须是绝对路径。`ipkg-build` 在打包中会切换工作目录，若输出路径写成相对路径，包可能被写到意外位置或报找不到目录。

### 8.3 验证 IPK 内容

本 SDK 环境下 IPK 是 gzip tar 形式，不应假定它是 `ar` 容器。因此下面的 `ar t` 失败属于格式判断错误，不代表包损坏。

正确检查方式：

```sh
CORE="$OUT_DIR/mihomo_git-r1_mipsel_24kc.ipk"
tar -tzf "$CORE"
tar -xOzf "$CORE" ./data.tar.gz | tar -tzf - | rg '^./usr/bin/mihomo$'
sha256sum "$CORE"
```

能够列出 `./usr/bin/mihomo`，且 SHA-256 与本文开头一致，即表示包内核心路径正确。

## 9. LuCI 包的构建与复用

LuCI 包的标准 SDK 构建目标是：

```sh
cd "$SDK"
PATH="$PWD/.host-tools:$PATH" \
make package/feeds/minimihomo/luci-app-minimihomo/compile V=sc
```

本次过程中，该目标需要先构建 LuCI 的 host 工具，最终在旧版 `contrib/lemon.c` 上被新 GCC 的函数原型检查阻断，典型报错为：

```text
conflicting types for FindRulePrecedences
conflicting types for FindFirstSets
conflicting types for FindStates
```

这是 OpenWrt 23.05/LuCI host 工具与新宿主 C 编译器的兼容问题，而不是 MiniMihomo LuCI 前端代码错误。解决方向是为 LuCI host 工具同样使用 GNU17 包装器，或修补 lemon 的旧式函数声明；本次没有为了一个架构无关包继续扩大 SDK 修改范围。

本次使用的是已从同版本 `r17` 源码验证生成的：

```text
luci-app-minimihomo_2.0.0-r17_all.ipk
```

之所以可以复用，是因为：

- 它的控制字段是 `Architecture: all`；
- 包中是 LuCI 页面、控制器、初始化脚本等文本资源，不包含 ARM 或 MIPS 原生机器码；
- 已确认其中包含 `www/luci-static/resources/view/minimihomo/nodes.js`，即本次节点与策略组默认折叠的 r17 前端。

但 `all` 只表示 CPU 无关，仍需保证路由器的 OpenWrt/LuCI 版本满足该包声明的依赖；不能把任何年代的 LuCI 包随意装到任何系统上。

## 10. 安装到路由器

把两个 IPK 上传到路由器 `/tmp`，先安装核心，再安装 LuCI：

```sh
opkg install /tmp/mihomo_git-r1_mipsel_24kc.ipk
opkg install /tmp/luci-app-minimihomo_2.0.0-r17_all.ipk
```

如果替换旧版本，建议先记录当前版本与配置，再覆盖安装。插件配置位于 `/etc/config/minimihomo`，完整 YAML 和订阅缓存位于插件所使用的配置目录；不要为了升级 IPK 随意删除这些数据。

安装后检查：

```sh
mihomo -v
opkg status mihomo
opkg status luci-app-minimihomo
/etc/init.d/minimihomo restart
logread | grep -i minimihomo
```

若只想验证 YAML，不启动服务，可使用：

```sh
mihomo -t -d /etc/minimihomo -f /etc/minimihomo/config.yaml
```

这里的“测试成功”只说明 YAML 语法和 Mihomo 配置能被读取；订阅是否可访问、节点是否可连通、TUN 是否满足内核条件仍需要在实际启动日志中确认。

## 11. 常见问题速查

| 现象 | 根因 | 处理方式 |
| --- | --- | --- |
| `Please install GNU install` | 系统 `install` 来自 uutils，不符合 SDK 旧检查。 | 在 SDK `.host-tools` 中把 `install` 链接到 `/usr/bin/gnuinstall`，并调整 `PATH`。 |
| 单包编译却开始编译全部内核和固件 | SDK 的 `Config-build.in` 或旧 `.config` 默认启用了全量 profile/模块。 | 备份后关闭 `ALL*`、全 profile、无关 `kmod` 默认项，重新 `make defconfig`。 |
| Go 报 `bool is a keyword with -std=c23` | SDK 内旧 Go 引导源码不兼容 GCC 默认 C23。 | 用 `.host-tools/gcc` 包装器固定 `-std=gnu17`。 |
| Go 找不到 `gcc -std=gnu17` | 把带空格的命令当作 `CC` 可执行文件名传入。 | 使用无空格路径的 shell 包装器。 |
| `make package/mihomo/compile` 无规则 | 包实际位于 feed 下。 | 使用 `package/feeds/<feed>/<package>/compile`。 |
| SDK fakeroot 库找不到 | SDK host 工具库与当前宿主环境不协调。 | 用系统 `fakeroot` 调用 SDK `scripts/ipkg-build`。 |
| 设置 `LD_LIBRARY_PATH` 后系统命令报 GLIBC 符号错误 | 系统命令误加载 SDK 的旧 glibc。 | 不对系统 fakeroot/env 注入 SDK host 的库目录。 |
| `ar t xxx.ipk` 失败 | 该 SDK 输出的 IPK 是 gzip tar 容器。 | 用 `tar -tzf` 和解出 `data.tar.gz` 检查。 |
| LuCI 编译卡在 `lemon.c` | OpenWrt 23.05 LuCI host 工具与新 GCC 的原型检查不兼容。 | 使用 GNU17 wrapper 或单独修补旧式声明；架构无关包可在依赖兼容时复用。 |

## 12. 下次换 SDK 时的最小流程

1. 确认新 SDK 的 OpenWrt 大版本、目标、CPU 架构和 libc 与路由器固件一致。
2. 将本地 `minimihomo-feed` 加入 SDK feed，保持 `mihomo-source` 在本地可访问。
3. 先运行一次前置检查；若宿主工具不兼容，优先用 SDK 内 `.host-tools` 包装或链接解决，不修改全局系统工具。
4. 用 `make menuconfig` 或精简后的 `.config` 只选择目标设备和 MiniMihomo 必需依赖，避免全量 profile/module。
5. 先构建 SDK 的 Go host；遇到新 GCC/C23 问题就使用 `gnu17` 包装器。
6. 以 `GOOS=linux GOARCH=<目标> GOMIPS=softfloat CGO_ENABLED=0` 编译本地 Mihomo 源码。
7. 使用 `file`、`readelf` 验证 ELF 架构后，再封装 IPK。
8. 用 `tar` 检查 IPK 内容、计算 SHA-256。
9. 路由器上先安装核心，再安装 LuCI；最后以 `mihomo -t` 和服务日志验证。

## 13. 本次最重要的经验

1. **先确认“构建范围”再开始编译。** 单包构建却出现完整内核和全部模块，优先检查 SDK 的 Kconfig 默认规则，而不是等几个小时后才处理依赖错误。
2. **不要为了旧 SDK 改坏宿主系统。** SDK 专用的 `.host-tools` 包装器可控、可删除、可复现。
3. **交叉编译成功不等于可安装。** 必须同时验证 ELF 架构、IPK 架构字段、包内安装路径和路由器运行日志。
4. **`Architecture: all` 不等于零兼容性风险。** LuCI 文件不依赖 CPU，但仍依赖 OpenWrt/LuCI 的接口与包依赖版本。
5. **源码、SDK 修改和最终产物要分开管理。** 插件源码适合手动提交；SDK 内的临时兼容补丁和 `.host-tools` 应留在构建环境中，并记录在本文这类文档里。
